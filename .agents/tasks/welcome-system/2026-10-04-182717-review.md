# Shop Module Refactor Review

TypeScript refactor of Discord shop bot from JavaScript, implementing stock tracking, purchase guards, and multi-currency support. The module migrated from a standalone bot structure to a class-based architecture with four slash commands (shop, inventory, balance, revoke) and maintains backwards compatibility with legacy coins.json.

**Watch for:** Busy guard cleanup not guaranteed in exception paths (confirmed), select menu interaction type cast bypasses TypeScript safety (confirmed), refresh shop call updates wrong message (confirmed), refresh button uses deferUpdate/editReply instead of update (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

Stock tracking uses shop-sold.json and three functions (getSoldCount, incrementSold, decrementSold) that load and save on every call. The busyUsers Set guards the purchase handler to prevent double-deduct, but cleanup happens outside the try/finally that wraps role assignment, leaving the Set dirty if an early return fires.

The buildShop function assembles embed fields with `\u200B` names and inline layout, appends a full-buy field (inline: false), and uses parseEmoji to extract animated emoji IDs for the select menu. The function returns `{ embeds, components, files }` with an optional banner attachment.

The purchase handler deducts currencies and increments sold counts before assigning roles, and rolls back both on failure. The refresh call after purchase uses `interaction.editReply(refreshed)`, which updates the original /shop response instead of the shop embed the user is interacting with. The refresh button handler uses `i.deferUpdate()` then `i.editReply(...)` instead of `i.update(...)`.

<details>
<summary>Issues (4)</summary>

1. **Busy guard cleanup not guaranteed** — busyUsers.delete(userId) sits in a finally block, but early returns before that block (no targets, insufficient balance) leave userId in the Set forever. Move busyUsers.add into a try block that wraps all paths and ensure finally always runs.
2. **Type-unsafe interaction cast** — `(i as any).values[0]` bypasses TypeScript's type narrowing after `i.isStringSelectMenu()`. Use `i.values[0]` directly since the type guard already narrows the type.
3. **Refresh updates wrong message** — After purchase, `interaction.editReply(refreshed)` updates the original /shop response, not the ephemeral reply. Should be `i.message?.edit(refreshed)` to update the shop embed the user is looking at.
4. **Refresh button method mismatch** — Refresh button uses `i.deferUpdate()` then `i.editReply(...)` instead of the simpler `i.update(buildShop(...))`. While functional, it's not the idiomatic pattern and doesn't match the requirement.

## Stock tracking system

Three functions (getSoldCount, incrementSold, decrementSold) operate on shop-sold.json. Each call loads the entire file, modifies a single counter, and writes it back. Concurrent purchases will race on file writes.

## Purchase handler with busy guard

The busyUsers Set is declared at module level. The purchase handler checks membership, adds userId to the Set, and removes it in a finally block that wraps only the role assignment and refresh logic. Early returns (no targets, insufficient balance) fire before the try block begins, so userId remains in the Set.

The correct structure:

```typescript
if (busyUsers.has(userId)) { /* reply and return */ }
busyUsers.add(userId);
try {
  // all purchase logic, including filter and balance check
} finally {
  busyUsers.delete(userId);
}
```

The current structure:

```typescript
busyUsers.add(userId);
try {
  // filter and balance checks with early returns
  await i.deferReply();
  // deduct, assign, refresh
} finally {
  busyUsers.delete(userId);
}
```

After one insufficient-balance attempt, the user cannot purchase again until the bot restarts.

## buildShop function

The embed fields use `name: '\u200B'` (zero-width space) and `inline: true`. Each field's value is:

```
${item.emoji} **${item.name}**
${item.tag ? `**[${item.tag}]** ` : ''}${item.description}
> - **${formatNumber(item.prices.cowoncy)}** ${emojis.gem}
> - **${item.prices.blueTicket}** ${emojis.trophy}
> - **${item.prices.goldTicket}** 🏆
> - Còn ${stockLeft}/${item.stock} suất  (if stock defined)
```

The full-buy field is appended with `inline: false`.

The select menu uses parseEmoji to extract `{ id, animated }` from custom emoji strings. The function regex-matches `<a?:name:id>` and returns the id and animated flag. If parseEmoji returns undefined (static Unicode emoji), the code doesn't set an emoji, which could fail silently. The fallback `{ name: '🎁' } as any` for the "all" option bypasses type safety with `as any`.

## Refresh mechanism

The shop command's collector has a refresh button handler:

```typescript
if (i.customId === 'shop_refresh') {
  await i.deferUpdate();
  const refreshed = buildShop(i.client, userId);
  await i.editReply(refreshed);
  return;
}
```

The requirement says "Refresh button calls `i.update(buildShop(...))`". The code calls `i.deferUpdate()` then `i.editReply(...)`, which works but is not the idiomatic pattern.

After purchase, the handler refreshes the shop:

```typescript
const refreshed = buildShop(i.client, userId);
await interaction.editReply(refreshed).catch(() => {});
```

This updates `interaction` (the original /shop command), not `i` (the select menu interaction). The user is looking at an ephemeral reply from the select menu, but the code updates the public shop message. The requirement says "refresh shop via `interaction.message?.edit(buildShop(...))`". The code should be `await i.message?.edit(refreshed)`.

## Interaction type safety

The purchase handler casts the interaction to bypass TypeScript:

```typescript
const v = (i as any).values[0];
```

The type guard `i.isStringSelectMenu()` narrows the type to StringSelectMenuInteraction, which has a `values: string[]` property. The cast `(i as any)` defeats the type guard and bypasses safety.
