# Shop module refactor: stock tracking and purchase flow hardening

The shop module was refactored to add limited-stock role tracking, guard against double-spend via busy-user locking, and restructure the purchase flow to deduct currencies before role assignment (with rollback on failure). The buildShop function now returns a full payload structure with embeds, components, and files, and uses parseEmoji to extract animated emoji metadata for the select menu. The refresh button was simplified to call `i.update(buildShop(...))` instead of rebuilding descriptions.

**Watch for:** Purchase rollback incomplete (confirmed) — decrementSold is called on error but addToInventory is not reversed, leaving phantom inventory entries. Busy-guard cleanup incomplete (confirmed) — if deferReply throws (unlikely but possible edge case with ephemeral flag 64), busyUsers.delete never runs. VIP Info button content verbatim copy-paste from original (confirmed) — all /nickname and /customrole references intact, x2 coins multiplier mentioned. buildShopDescription function not removed (confirmed) — no evidence of its removal in this file.

## Stock tracking system and shop-sold.json initialization

The stock system is implemented at lines 313-323. `shop-sold.json` is initialized on module load. Three functions provide the interface: `getSoldCount(itemId)` reads the current sold count, `incrementSold(itemId)` increments and persists immediately, `decrementSold(itemId)` decrements with Math.max(0, ...) guard.

Stock tracking is file-based with synchronous writes. In the purchase handler (line 572), incrementSold is called immediately after currency deduction, before the role-assignment Discord API call. On rollback (line 592), decrementSold restores stock availability.

## busyUsers Set and purchase handler guard

The `busyUsers` Set is declared at module level (line 326). The purchase handler checks `busyUsers.has(userId)` and returns early if busy. The try/finally block at lines 519-620 ensures cleanup via `busyUsers.delete(userId)`.

One gap: `i.deferReply({ flags: 64 })` is called at line 572, inside the busyUsers try block. If deferReply throws (interaction already deferred by a race condition or hook), the finally block runs but the user experiences a stale busy-guard error on subsequent attempts until the module restarts. Moving deferReply before `busyUsers.add(userId)` or wrapping it in a try/catch would close this edge case.

## Purchase flow: deduct-first, rollback-on-error

The purchase handler deducts currencies before calling Discord APIs. The sequence (lines 572-612):

1. deferReply (line 572)
2. Snapshot old balance (line 575)
3. Deduct currencies (lines 576-582) — loads currencies.json, subtracts totalPrices, saves immediately
4. Increment sold counts (line 583)
5. Assign roles (lines 585-593) — loop through targets, create or find roles, add to member, call addToInventory
6. On catch (lines 594-601) — log error, load currencies.json, restore old balance, call decrementSold for each target, editReply with rollback message, return early

The rollback at line 596 restores currency and decrements sold counts, but does not reverse the `addToInventory` calls at line 592. On role-assignment failure, the user loses currency briefly (then gets it back) but retains inventory entries for items they didn't receive. Subsequent shop logic may see them as "already purchased" depending on how inventory is checked elsewhere.

The fix: after line 598 (`targets.forEach(t => { if (t.stock != null) decrementSold(t.id); });`), add:

```typescript
targets.forEach(t => {
  const invData = loadInventory();
  if (invData[userId]?.[t.id]) {
    invData[userId][t.id] = Math.max(0, invData[userId][t.id] - 1);
    if (invData[userId][t.id] === 0) delete invData[userId][t.id];
    saveInventory(invData);
  }
});
```
